# Section 4: Use Component

This section covers ESP-IDF's component system — what components are, the different kinds you'll encounter, and how a component is structured. You'll then put that into practice with two hands-on examples: reading a button using the built-in GPIO driver, and reading the same button using a community-published button component.

:::info

Make sure you've completed [**Section 1: Set Up Environment**](./esp-idf-installation), [**Section 2: Run Example**](./run-example), and [**Section 3: Create Project**](./create-project) before starting this section.

:::

---

## 1. What Are ESP-IDF Components?

ESP-IDF is built around a modular architecture. Rather than one monolithic codebase, functionality like the OS, networking stacks, and peripheral drivers is split into independent, reusable **components**. During a build, each component is compiled into a static library, then linked into the final application alongside your own code.

This modularity means you can mix ESP-IDF's built-in components with your own custom components and with third-party components published by the community — combining pieces as needed rather than reinventing them. The main payoffs are clearer separation between pieces of a project, easier code reuse, and simpler long-term maintenance as a project grows.

---

## 2. Types of Components

ESP-IDF projects generally work with three kinds of components:

- **Built-in components** — ship with ESP-IDF itself, living inside the ESP-IDF installation's own `components/` folder. These cover things like low-level drivers, networking stacks, and FreeRTOS. You can include their headers directly with no extra setup.
- **Project components** — components you create yourself inside your project's own `components/` folder. Useful for splitting out project-specific, reusable pieces of logic so `main/` doesn't become a dumping ground for everything.
- **Managed (external) components** — published by the community to the [ESP Component Registry](https://components.espressif.com/) and pulled into your project automatically by the IDF Component Manager. These land in a `managed_components/` folder once downloaded.

---

## 3. What Makes Up a Component

A typical component consists of:

- **Source files** implementing its functionality.
- **Header files** declaring the interface other code can call.
- **`CMakeLists.txt`** — registers the component with the build system: which source files to compile, what it depends on, and any optional feature flags.
- **`idf_component.yml`** (optional) — lists the component's own dependencies and their versions, so the Component Manager can resolve and fetch them automatically.

---

## 4. Where Components Live in a Project

A project that uses several components might look like this:

```text
myProject/
├── CMakeLists.txt
├── sdkconfig
├── dependencies.lock
├── main/
│   ├── CMakeLists.txt
│   ├── main.c
│   ├── src1.c
│   └── idf_component.yml
├── components/
│   ├── component1/
│   │   ├── CMakeLists.txt
│   │   ├── Kconfig
│   │   └── src1.c
│   └── component2/
│       ├── CMakeLists.txt
│       ├── Kconfig
│       ├── src1.c
│       └── include/
│           └── component2.h
├── managed_components/
│   └── namespace__component-name/
│       ├── CMakeLists.txt
│       ├── idf_component.yml
│       ├── src1.c
│       └── include/
│           └── src1.h
└── build/
```

- **`main/`** — every project needs exactly one "main" component (you can rename it) holding the top-level application logic. It has its own `CMakeLists.txt`, and optionally its own `idf_component.yml` if it needs dependencies of its own.
- **`components/`** — your project-specific components. If a component name here collides with one from elsewhere, the one under `components/` wins.
- **`managed_components/`** — owned by the Component Manager. Don't hand-edit anything in here; if you need to modify a managed component, copy it into `components/` first and edit that copy instead.
- **`idf_component.yml`** — can appear inside `main/`, inside any component under `components/`, or inside a managed component. It's only needed when that component has dependencies to declare.
- **`dependencies.lock`** — auto-generated by the Component Manager to pin the exact versions of every managed component in use. Don't edit it by hand — it only gets created once some `idf_component.yml` exists in the project.

## 5. Example: Reading a Button With the Built-In GPIO Driver

First, let's use ESP-IDF's built-in GPIO driver to read a physical button's state — no external component needed.

### 5.1 Wire It Up

You'll need:

- 1x pushbutton
- 1x breadboard
- Jumper wires
- An ESP32-series development board

Wire one leg of the button to a GPIO pin, and the other leg to ground (GND). Check your board's pinout for a suitable input-capable pin — this tutorial uses GPIO7 as an example.

### 5.2 Register the GPIO Driver Dependency

1. Create a new project the same way you did in [Section 3](./create-project#2-create-a-project-from-scratch).
2. Add the driver header to `main.c`:

```c
#include "driver/gpio.h"
```

3. Declare the dependency in `main/CMakeLists.txt`:

```text
idf_component_register(SRCS "main.c"
                        INCLUDE_DIRS "."
                        REQUIRES esp_driver_gpio)
```

### 5.3 Example Code

Replace `main/main.c` with:

```c
#include <stdio.h>
#include "driver/gpio.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

#define BUTTON_GPIO GPIO_NUM_7

void app_main(void)
{
    gpio_config_t io_conf = {
        .pin_bit_mask = (1ULL << BUTTON_GPIO),
        .mode = GPIO_MODE_INPUT,
        .pull_up_en = GPIO_PULLUP_ENABLE,
        .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type = GPIO_INTR_DISABLE
    };
    gpio_config(&io_conf);

    while (1) {
        int level = gpio_get_level(BUTTON_GPIO);
        printf("Button value: %d\n", level);
        vTaskDelay(pdMS_TO_TICKS(20));
    }
}
```

### 5.4 Build, Flash, and Observe

Set your target, port, and flash method as covered in [Section 2](./run-example#13-configure-target-port-and-flash-method), then run **Build, Flash and Monitor**.

- With the button unpressed, the internal pull-up keeps GPIO7 high, so you'll see `Button value: 1`.
- With the button pressed (pulling the pin to GND), you'll see `Button value: 0`.

### 5.5 How the Code Works

- `gpio_config_t` bundles all the pin configuration into one struct, applied in a single `gpio_config()` call.
- `.pin_bit_mask = (1ULL << BUTTON_GPIO)` selects which pin(s) this config applies to. Shifting `1ULL` left by the pin number sets exactly one bit — the one corresponding to GPIO7 — producing a mask that targets that pin only.
- `.mode = GPIO_MODE_INPUT` puts the pin in input mode.
- `.pull_up_en = GPIO_PULLUP_ENABLE` turns on the internal pull-up resistor, so the pin reads a stable high level when the button isn't pressed rather than floating.
- Inside the loop, `gpio_get_level()` reads the pin, and a short `vTaskDelay()` keeps the polling loop from hogging the CPU.

:::note

Which GPIOs are safe to use varies by chip — some pins are reserved internally. Check your chip's specific pin reference before wiring.

:::

## 6. Example: Reading a Button With an External Component

Polling a raw GPIO works for a quick demo, but real button handling needs debouncing and event detection (single-click, double-click, long-press, and so on). Rather than writing that logic yourself, you can pull in a ready-made community component.

This example uses the [`espressif/button`](https://components.espressif.com/components/espressif/button) component from the ESP Component Registry.

### 6.1 Wire It Up

Same circuit as the previous example: one button leg to a GPIO pin (GPIO7 in this example), the other to GND.

### 6.2 Add the Component as a Dependency

1. Open the [ESP Component Registry](https://components.espressif.com/) and find the `espressif/button` component.
2. The registry page gives you a command like:

```text
idf.py add-dependency "espressif/button^4.1.5"
```

3. Open the ESP-IDF terminal from within VS Code and run that command from your project's root directory. This updates your project's `idf_component.yml` and downloads the component into `managed_components/`.
4. Include the component's headers in your code and call its API, as shown below.

### 6.3 Example Code

Replace `main/main.c` with:

```c
#include <stdio.h>
#include "driver/gpio.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"
#include "iot_button.h"
#include "button_gpio.h"

#define BUTTON_GPIO GPIO_NUM_7
#define BUTTON_ACTIVE_LEVEL 0

static const char *TAG = "button_example";

static void button_single_click_cb(void *arg, void *usr_data)
{
    ESP_LOGI(TAG, "BUTTON_SINGLE_CLICK");
}

static void button_double_click_cb(void *arg, void *usr_data)
{
    ESP_LOGI(TAG, "BUTTON_DOUBLE_CLICK");
}

void app_main(void)
{
    const button_config_t btn_cfg = {0};
    const button_gpio_config_t btn_gpio_cfg = {
        .gpio_num = BUTTON_GPIO,
        .active_level = BUTTON_ACTIVE_LEVEL,
    };

    button_handle_t gpio_btn = NULL;
    esp_err_t ret = iot_button_new_gpio_device(&btn_cfg, &btn_gpio_cfg, &gpio_btn);
    if (ret != ESP_OK) {
        ESP_LOGE(TAG, "Button create failed");
        return;
    }

    iot_button_register_cb(gpio_btn, BUTTON_SINGLE_CLICK, NULL, button_single_click_cb, NULL);
    iot_button_register_cb(gpio_btn, BUTTON_DOUBLE_CLICK, NULL, button_double_click_cb, NULL);

    while (1) {
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

### 6.4 Build, Flash, and Observe

Build, flash, and monitor as before.

- A single click logs: `I (xxxx) button_example: BUTTON_SINGLE_CLICK`
- A quick double click logs: `I (xxxx) button_example: BUTTON_DOUBLE_CLICK`

### 6.5 How the Code Works

The `espressif/button` component recognizes several event types out of the box — press, release, single-click, double-click, long-press-start, long-press-hold, and more — and lets you register a separate callback for each one.

- `iot_button.h` provides the component's core API and event type definitions; `button_gpio.h` adds the config struct and constructor specific to GPIO-connected buttons (the component also supports ADC and matrix buttons).
- `button_config_t` covers general button settings, while `button_gpio_config_t` covers GPIO-specific ones like the pin number and active level.
- `iot_button_new_gpio_device()` creates a button instance from that configuration.
- `iot_button_register_cb()` attaches a callback to a specific event type on that button handle. Pass `NULL` for the `event_args` parameter unless the event type needs extra configuration (for example, a custom long-press duration).
- Because the component runs its own detection logic internally (backed by a FreeRTOS software timer), `app_main`'s loop doesn't need to poll anything — it just needs to stay alive so the task doesn't exit.

## 7. Creating Your Own Component

You can scaffold a new component two ways:

- **From VS Code:** open the command palette (`Ctrl + Shift + P`) and run **ESP-IDF: Create New ESP-IDF Component**.
- **From the command line:**

```text
idf.py create-component <component_name>
```

Either approach generates the basic folder structure (source file, header, and `CMakeLists.txt`) for you to fill in.

---

## 8. Board Support Packages (BSPs)

A **Board Support Package** is a component that packages up pin configuration and driver initialization for a specific board's onboard hardware — displays, touch controllers, audio codecs, SD/TF card slots, LEDs, buttons, and so on — behind a single, consistent API. Using a BSP means you don't have to re-derive pin mappings and init sequences for hardware that's already been wired up on the board for you.

Like any other component, a BSP can be pulled into a project through the Component Manager via `idf_component.yml`.
